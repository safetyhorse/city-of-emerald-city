Layout patterns for lists & tables

First ask: is this actually tabular data (records with shared fields), or a one-dimensional list of items? The answer picks your tool.

Tabular data → use a <table>

A permit fee schedule is genuinely tabular: every row is a record, every column a shared field. Use the real element — it's correct, accessible, and expected by screen readers. Then make it responsive with CSS. Two honest ways:

Way A — let it scroll (safest)

Recommended default. Wrapping the table in an overflow-x: auto box keeps every bit of table semantics intact. Nothing changes for assistive tech; narrow screens just scroll sideways.

A one-dimensional list → arrange it

A list of city services isn't tabular — it's a sequence of items. There's no "right" element beyond a list; the question is how to arrange it so it doesn't waste a tall, skinny column. Same 20 items below, three tools. Drag each box to compare.

Flexbox — content-driven

Items size to their content and wrap. The right edge is ragged and columns don't line up, because each item is only as wide as its text. Reach for flexbox when the content should decide the sizing (tags, buttons, nav).

Grid — layout-driven

Equal columns, aligned both horizontally and vertically, packing in as many as fit via repeat(auto-fit, minmax(9rem, 1fr)) — and it reflows with no media query. This is the set-and-forget pattern most long lists want.

Multi-column — when reading order matters

For an alphabetical or sequential list you often want to read down each column, then across — like a phone book. Grid and flexbox flow across-then-down and can't do this. columns: 9rem can, and it also reflows with no media query. The right tool for A–Z indexes.

Structuring a whole page → grid outside, flex inside

When you're building the page shell itself, the same distinction scales up. Grid places the big regions (it's two-dimensional and you want named structure); flexbox arranges what's inside a region (a single run of items, like the menu); and position: sticky is a behavior you add on top — it needs neither grid nor flex. The takeaway line: grid places the regions, flexbox arranges what's in them, and sticky is a behavior added on top. If you're positioning in two directions at once, that's grid; if it's a single run of items, that's flex.

How to choose

Is it tabular data (records × fields)? Use a <table>, then make it responsive (scroll = safest; reflow = prettier, test with a screen reader).

Is it a list of items? Then arrange it:
• Flexbox when the content sets the size and a ragged wrap is fine.
• Grid (auto-fit + minmax) when you want tidy, equal, aligned columns — the usual winner for long lists.
• Columns (columns) when reading order down each column matters.

Building the whole page shell? Grid places the regions (grid-template-areas), flexbox arranges what's inside each one, and position: sticky is a behavior on top.

The one-line mental model: flexbox = one axis, content-driven; grid = two axes, layout-driven. All of these reflow with no media query — they respond to available space on their own.
